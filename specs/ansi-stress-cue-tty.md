# Стресс-тест ANSI-рендера через cue-tty

## Контекст

Живой интерфейс Automata продолжает визуально лагать, хотя точечные тесты Portalis проходят. Текущие проверки не воспроизводят длительный поток смешанных ANSI, Unicode, synchronized output, scrolling и частичных PTY-чанков в настоящем псевдотерминале.

## Цель

Создать детерминированный стресс-сценарий Portalis и проверить его через cue-tty при фиксированном размере терминала. Тест должен обнаруживать повреждение экрана, размазывание динамической строки и недопустимую задержку обработки.

## Что изменится

1. `testdata/ansi-stress/main.go` — тестовое TUI-приложение, которое прогоняет сложные последовательности через Portalis.
2. `ansi_stress_test.go` — unit/regression тест потока, чанкинга, итогового экрана и времени обработки.
3. `scripts/test-ansi-stress-cuetty.sh` — визуальный сценарий cue-tty.
4. `testdata/pi-live/main.go` — Bubble Tea harness, в котором Portalis запускает настоящий Pi.
5. `pi_live_cuetty_test.go` — два live E2E через cue-tty и локальную модель: прямой Pi и Pi внутри tmux.
6. `cuetty-artifacts/ansi-stress/`, `cuetty-artifacts/pi-live/` и `cuetty-artifacts/pi-tmux-live/` — снимки, состояние, события, временная шкала и отчёт.

## Детали реализации

1. Генератор создаёт детерминированный поток из сотен кадров:
   - DECSET 2026;
   - абсолютные и относительные перемещения курсора;
   - очистка, вставка и удаление строк/символов;
   - scroll region и scrolling;
   - SGR 16/256/truecolor;
   - OSC 7 и OSC 8;
   - DEC line drawing;
   - ASCII, CJK, emoji, ZWJ, variation selectors и combining marks.
2. Поток подаётся чанками разного фиксированного размера, включая разрывы внутри UTF-8 и CSI/OSC.
3. Итоговый экран содержит единственный динамический статус `FRAME 0400`, контрольные границы и маркер `STRESS PASS`.
4. Unit-тест проверяет:
   - отсутствие старых `FRAME`;
   - ширину каждой строки;
   - wide-cell invariants;
   - детерминированный checksum;
   - верхний предел времени обработки без sleep.
5. Cue-tty запускает собранный fixture в PTY 100×30, сохраняет до/после и проверяет `STRESS PASS`, `FRAME 0400`, отсутствие `FRAME 0399` и `CORRUPTION`.
6. Артефакты включают `before/after.render.txt`, `before/after.state.json`, `events.log`, `timeline.md`, `report.md`.
7. Live-сценарий запускает `pi --no-session --model home-pc/qwen-3.5-9b` внутри Portalis Emulator.
8. Второй live-сценарий запускает `tmux`, внутри которого выполняется `pi --no-session --model home-pc/qwen-3.5-9b`.
9. Промпты выбраны так, чтобы ответ помещался в видимую область 120×40 и конечный маркер не уходил в scrollback:
    - Первый: ~35 строк ASCII кода (Go, Python, JSON, shell, SQL), завершается маркером `PZ9Q7END42`.
    - Второй: ~25 строк ASCII путей и конфигов, завершается маркером `RX8M3END77`.
10. Cue-tty отправляет два потоковых промпта, регулярно снимает экран во время генерации и проверяет:
   - ответы дошли до уникальных конечных маркеров;
   - во время генерации видна не более чем одна строка `Working...`;
   - команды чтения экрана не зависают;
   - после двух ответов ввод остаётся работоспособным.

## Критерии приёмки

- [x] Unit stress-тест стабильно проходит.
- [x] Поток корректен при нескольких схемах разбиения на чанки.
- [x] На итоговом экране ровно один актуальный статус.
- [x] Все строки имеют ожидаемую видимую ширину.
- [x] Cue-tty сценарий проходит при размере 100×30.
- [x] Визуальные артефакты сохранены.
- [x] `go test ./...` и `go vet ./...` проходят.
- [x] Portalis запускает Pi с `--no-session --model home-pc/qwen-3.5-9b`.
- [x] Cue-tty отправляет Pi минимум два промпта и получает оба конечных маркера.
- [x] Ни один ASCII streaming snapshot не содержит более одной строки `Working...`.
- [x] Live Pi артефакты сохранены.
- [x] Portalis запускает tmux, внутри которого работает Pi с заданной моделью.
- [x] Tmux-сценарий проходит те же streaming и responsiveness проверки.
