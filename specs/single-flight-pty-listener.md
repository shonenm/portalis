# Единственная цепочка чтения PTY

## Контекст

Во время потокового ответа Pi после прерывания операции и запуска нового ответа Portalis показывает несколько строк `Working...`, старые разделители и повторный status bar.

Проблема воспроизведена в изолированной Automata:

1. Запустить длинный ответ Pi.
2. Во время `Working...` нажать `Escape`.
3. Запустить второй длинный ответ.
4. На втором потоке появляется две строки `Working...`.

Raw PTY trace, проигранный строго в записанном порядке, содержит не больше одного `Working...`. Следовательно, Pi отправляет корректный поток, а порядок нарушается в host-цикле.

Причина: Automata восстанавливает активную сессию и запускает `Emulator.Listen`. При выборе уже работающего чата повторный `Emulator.Start` возвращает `PtyReadyMsg{AlreadyRunning: true}`. `Emulator.Update` запускает ещё один `Listen`, поэтому несколько Bubble Tea commands одновременно читают один канал `Pty.Output`. Полученные chunks доставляются парсеру не в исходном порядке.

Дополнительно `TermPanel.View` содержит временное production-логирование каждого кадра с несколькими `Working...`. Файл `/tmp/automata-termpanel-debug.log` вырос до 40 ГБ.

## Цель

Гарантировать не более одного ожидающего `Listen` на один `Emulator`, сохранить исходный порядок PTY chunks и убрать неограниченное диагностическое логирование кадров.

## Что изменится

1. `portalis/emulator.go` — single-flight состояние listener и обработка `AlreadyRunning`.
2. `portalis/emulator_batch_test.go` — regression-тест единственной listener-цепочки.
3. `automata/internal/ui/term_panel.go` — удалить временное логирование полных кадров.
4. Контекстные файлы обоих проектов — записать проблему и решение.

## Детали реализации

1. Добавить в `Emulator` булево состояние ожидающего listener под существующим `e.mu`.
2. `Emulator.Listen`:
   - вернуть `nil`, если PTY отсутствует или listener уже ожидает данные;
   - перед возвратом команды отметить listener ожидающим;
   - обернуть `Pty.Listen`, чтобы перед возвратом сообщения в Bubble Tea сбросить состояние ожидающего listener;
   - после обработки `PtyOutputMsg` существующий вызов `e.Listen()` создаёт ровно следующего читателя.
3. В обработчике `PtyReadyMsg` не запускать новый listener, если `AlreadyRunning == true`.
4. Сбрасывать listener-состояние при создании нового терминала и остановке Emulator.
5. Добавить regression-тест:
   - первый `Listen()` возвращает команду;
   - второй `Listen()` до получения данных возвращает `nil`;
   - после завершения первой команды следующий `Listen()` снова доступен;
   - порядок двух последовательно переданных chunks сохраняется.
6. Удалить из `TermPanel.View` вызов `logTermPanelView` и связанные глобальные mutex/counter/imports. Production UI не должен записывать полный экран на каждый кадр.
7. Существующий файл `/tmp/automata-termpanel-debug.log` не удалять автоматически; его очистка выполняется только с явного разрешения пользователя.

## Критерии приёмки

- [x] На один `Emulator` существует не больше одного ожидающего listener.
- [x] `PtyReadyMsg{AlreadyRunning: true}` не создаёт listener.
- [x] Regression-тесты проходят после исправления.
- [x] Live-сценарий `stream → abort → новый stream` после фикса наблюдал не больше одного `Working...`.
- [x] Raw PTY chunks применяются парсером в исходном порядке.
- [x] Automata больше не пишет `/tmp/automata-termpanel-debug.log`.
- [x] `go vet ./...` и `go test ./...` проходят в Portalis.
- [x] `go vet ./...`, `go test ./...` и `go build -o automata .` проходят в Automata.
